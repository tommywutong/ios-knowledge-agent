# 符号绑定与重定位

## 一句话总结

符号绑定是动态链接器（dyld）将符号引用解析为具体内存地址的过程，分为**惰性绑定（lazy binding）**和**非惰性绑定（non-lazy binding）**两种方式，前者在符号首次被调用时才触发，后者在装载库时立即完成 [1]。

## 核心原理

1. **惰性 vs 非惰性符号**：惰性符号的绑定推迟到第一次调用时执行，非惰性符号在包含它的库加载时立即绑定。两者实际的绑定过程相同，仅触发时机不同 [1]。

2. **绑定机制（Mach‑O）**
   - 非惰性符号：需要间接跳转是因为无法在 `__TEXT` 段（可执行代码）写入数据，也无法在 `__DATA` 段（可写数据）放置可执行指令，因此跳转指令通过一次额外的指针解引用来实现 [3]。
   - 惰性符号：静态链接器将惰性符号指针初始化为指向 `__stub_helper` 中的代码，而非简单的 0。`__stub_helper` 代码将符号在懒加载指针表中的偏移量压栈，然后跳转到 `dyld_stub_binder`（这是一个非惰性绑定的符号）[3]。
   - `dyld_stub_binder` 执行完绑定后，更新 `__la_symbol_ptr` 中的指针条目，后续调用直接跳转到该指针，不再经过桩 [7]。

3. **bind opcodes**：dyld 通过 `__LINKEDIT` 段中的绑定 opcodes 序列来驱动绑定。例如 `BIND_OPCODE_SET_DYLIB_ORDINAL_IMM`、`BIND_OPCODE_SET_SYMBOL_TRAILING_FLAGS_IMM`、`BIND_OPCODE_DO_BIND` 等。非惰性符号（如 `dyld_stub_binder`）和惰性符号（如 `_printf`）分别由 `__bind` 和 `__lazy` 区域的 opcodes 描述 [9]。

4. **绑定流程示意（Mach‑O）** [7]
   - **启动阶段（非惰性绑定）**：dyld 解析 App 的 Mach‑O 头 → 读取 `LC_LOAD_DYLIB` → mmap 加载依赖库 → 通过导出表 Trie 树查询符号地址 → 更新 `__got`（全局偏移表）条目。
   - **运行时阶段（惰性绑定）**：首次调用函数 → 执行 `__stubs` 桩代码 → 调用 `_dyld_stub_binder` → 解析 lazy bind opcodes → 通过间接符号表找到符号名 → 查询导出表 → 计算真实地址 → 修改 `__la_symbol_ptr` → 跳转到函数实现。
   - **后续调用**：直接通过 `__la_symbol_ptr` 跳转到已绑定的地址，不再触发桩。

5. **fishhook 的绑定修改**：fishhook 通过遍历 Load Commands 找到 `__LINKEDIT` 段、`LC_SYMTAB`、`LC_DYSYMTAB`，再遍历 `__DATA`/`__DATA_CONST` 下 `S_LAZY_SYMBOL_POINTERS` 和 `S_NON_LAZY_SYMBOL_POINTERS` 类型的 Section，逐个重绑定符号 [4]。

6. **dyld 版本演进与优化**
   - **dyld 3（iOS 13+）**：引入 Launch Closure，缓存 Mach‑O 元数据的解析结果（包括需要 Rebase 的指针位置列表、需要 Bind 的符号及其目标位置等），避免每次启动重复解析。但 Rebase/Bind 操作本身仍需执行，因为 slide 值每次启动不同 [11]。
   - **dyld 4（iOS 15+）**：引入 **Chained Fixups**，将修正信息直接编码在指针值中，指针之间通过 `next` 字段形成链表，不再需要单独的地址列表，减少存储开销和随机访问导致的缓存不友好 [11][12]。同时支持 Page‑in Linking，按需修复页面，减少启动时内存占用 [12]。

7. **Light ELF 中的 lazy binding 相关**：传统 ELF 的惰性绑定依赖 `DT_JMPREL` 表的随机访问。Light ELF 改用 CREL（紧凑重定位格式），由于 CREL 的顺序特性，保留惰性绑定需要额外的内存分配来存放解码后的 `JUMP_SLOT` 重定位 [2]。（注：此条为 ELF 平台，与 Mach‑O 实现不同）

## 关键细节与易错点

- **惰性绑定不是简单填充 0**：静态链接器将懒加载符号指针填充为 `__stub_helper` 中对应入口的地址，而非 0，因此第一次跳转才被导向绑定过程 [3]。
- **`__stub_helper` 区域增长**：每个惰性符号在 `__stub_helper` 中增加两条指令来压入不同的偏移量，以便区分是哪个符号被调用 [3]。
- **非惰性绑定的间接原因**：不能直接修改 `__TEXT` 段（只读可执行），也不能在 `__DATA` 段放置可执行代码，所以必须通过额外一层指针（如 `__got`）间接跳转 [3]。
- **Chained Fixups 不缓存 slide 相关数据**：Launch Closure 缓存的内容与 slide 无关，slide 每次启动由 ASLR 随机生成，因此 Rebase/Bind 操作本身在每次启动仍然需要执行 [11]。
- **fishhook 工作范围**：它针对的是 `__DATA`/`__DATA_CONST` 中 `S_LAZY_SYMBOL_POINTERS` 和 `S_NON_LAZY_SYMBOL_POINTERS` 类型的 Section，重写指针条目以实现符号替换 [4]。
- **ELF 与 Mach‑O 的区别**：上述大部分描述针对 Mach‑O/dyld。ELF 使用 PLT/GOT 机制实现惰性绑定，而 Mach‑O 使用 `__stubs` + `__stub_helper` + `dyld_stub_binder` [7][3]。材料中未比较两者，但需注意概念混淆。

## 高频追问

**1. 惰性绑定和动态库加载有什么关系？为什么有的框架会禁用惰性绑定？**
- 惰性绑定将符号的解析推迟到第一次调用时，可以减少启动时间。但某些场景下（如安全要求、避免运行时绑定失败导致崩溃）可能会通过设置 `LD_BIND_NOW` 环境变量或标记 `DF_1_NOW` 强制非惰性绑定 [5]。材料未直接讨论禁用原因，仅提到非惰性绑定在库加载时立即完成 [1]。

**2. `dyld_stub_binder` 本身的绑定为什么是非惰性的？**
- 因为 `dyld_stub_binder` 是 dyld 内部的符号，必须尽早可用，否则桩代码无法跳转到绑定函数。在 Mach‑O 示例中，`dyld_stub_binder` 被明确列为非惰性绑定符号 [9]。

**3. Chained Fixups 如何减少 Rebase/Bind 的开销？**
- 传统方式在 `__LINKEDIT` 段单独存储每个需要修正的指针地址列表（每个位置 8 字节），dyld 需要随机跳转到这些地址执行加 slide 操作。Chained Fixups 将修正信息编码在指针值本身，指针通过 `next` 字段形成链表，dyld 可以顺序遍历链表，减少存储和随机访存，提升缓存友好性 [11][12]。

**4. fishhook 如何实现符号劫持？**
- 它通过 Mach‑O Load Commands 找到 `__LINKEDIT` 段、符号表（`LC_SYMTAB`）、动态符号表（`LC_DYSYMTAB`），然后找到 `__DATA`/`__DATA_CONST` 中懒加载和非懒加载符号指针 Section，遍历 Section 中的每个条目，将对应的符号指针修改为目标函数地址 [4]。

**5. Launch Closure 缓存了什么？**
- 缓存与 slide 无关的元数据：需要 Rebase 的指针位置列表、需要 Bind 的符号及其目标位置、依赖库加载顺序、初始化器（Initializer）调用顺序。不缓存 slide 值及最终指针地址，因此 Rebase/Bind 操作仍需执行 [11]。
