# 模块化与依赖管理

## 一句话总结

模块化是将代码分割成独立的单元（如 Swift Package 或 Framework）以改善架构的方法，依赖管理工具（Swift Package Manager、CocoaPods 等）负责获取、集成和解析这些模块之间的依赖关系。

## 核心原理

1. **模块化的价值**
   - 将 Model 移入单独的模块是改进架构的关键步骤，能提前暴露问题并防止未来问题 [12]。

2. **Swift Package Manager (SPM)**
   - 是 Apple 官方工具，同时提供构建系统和依赖管理功能 [2]。
   - 与 Xcode 深度集成，无需额外工作区文件 [5]。
   - 可以创建“内联 Swift Package”——即在项目目录内创建并与 Xcode 项目关联，避免子 Framework 导致的 `.xcodeproj` 膨胀和多平台副本问题 [3]。
   - 也可以仅用于依赖解析，而不作为主要构建系统 [1][2]。
   - 依赖声明支持远程仓库（URL）、本地路径（path）、分支、版本范围等 [8][9]。
   - 支持指定库类型为 `.dynamic`（动态库）[7]。
   - Swift 社区提供了 [Swift Package Index](https://swiftpackageindex.com) 帮助发现支持 SPM 的包 [10]。

3. **CocoaPods**
   - 广泛使用的 iOS 依赖管理器，支持 Objective-C 和 Swift，能处理复杂依赖和多平台目标。
   - 通过生成额外的工作区文件在 Xcode 内置系统之外运行 [5]。

4. **Clang Modules（模块映射）**
   - `module.modulemap` 文件定义 Framework 模块的结构和暴露的接口，Clang 通过 `HeaderSearch.cpp` 按顺序查找：
     1. `Framework.framework/Modules/module.modulemap`（推荐位置）
     2. `Framework.framework/module.map`（已废弃，产生警告）
     3. `Framework.framework/Modules/module.private.modulemap` [11]。

5. **模块化的替代方案：monolithic framework（整体式框架）**
   - 在 SPM 正式随 Xcode 发布前，作者只能使用无依赖的整体式框架，原因是第三方依赖管理工具无法优雅实现静态链接和透明 Xcode 集成 [4]。

## 关键细节与易错点

1. **SPM 的依赖解析与构建系统可分离**
   - 即使不想用 SPM 作为主构建系统，也可以用 `swift package fetch` 仅获取依赖，然后让 Xcode 项目引用下载的文件 [1][2]。

2. **内联 Swift Package 与子 Framework 的区别**
   - 内联 Swift Package 避免 `.xcodeproj` 膨胀，且无需为每个平台创建单独的 Framework 目标；如果项目无法使用 SPM，创建子 Framework 仍然是较好的方法 [3]。

3. **CocoaPods 的工作机制**
   - 它不会修改 Xcode 内置的构建系统，而是生成 `.xcworkspace` 文件，开发者需打开该工作区而非原 `.xcodeproj` [5]。

4. **模块映射查找顺序的陷阱**
   - 开发者在放置 `module.modulemap` 时应使用 `Modules/` 子目录下的名称，旧版 `module.map` 虽仍能工作但会产生警告 [11]。

5. **SPM 依赖的本地路径与远程 URL**
   - 使用 `.package(path:)` 时注意版本范围写法（如 `"1.0.0"..<"2.0.0"`），使用 `.package(url:)` 时推荐 `.upToNextMajor(from:)` 或精确版本 [7][8][9]。

6. **Unit Testing 与模块边界**
   - 模块化设计可改善测试隔离性，避免跨模块测试的耦合问题（材料中提到子 Framework 在单元测试中存在与“xcodeproj bloat”类似的问题）[3]。

## 高频追问

**Q：我只想用 SPM 下载依赖，但不用它来构建代码，能实现吗？**
A：可以。SPM 支持 `swift package fetch` 命令仅获取依赖，之后让 Xcode 项目直接引用下载的文件 [1][2]。但需注意这种用法需要额外工程步骤（如添加文件引用）[1]。

**Q：CocoaPods 和 SPM 的主要区别是什么？**
A：CocoaPods 需生成额外的 `.xcworkspace` 文件，不在 Xcode 内置工具链中 [5]；SPM 是 Apple 官方工具，与 Swift 和 Xcode 原生集成，无需额外工作区文件 [5]。SPM 同时是构建系统和依赖管理器 [2]，而 CocoaPods 专注依赖管理。

**Q：为什么作者在早期不推荐 monolithic framework，而后来推荐用 SPM 创建内联包？**
A：早期第三方依赖管理工具无法实现静态链接和透明 Xcode 集成，所以作者只能采用整体式框架 [4]；SPM 正式发布后，它提供了更优雅的模块化方案，比如内联 Swift Package 避免了 `.xcodeproj` 膨胀和多平台副本问题 [3]。

**Q：Clang Module Map 中 `umbrella header` 和 `module * { export * }` 的作用是什么？**
A：`umbrella header` 指定一个“伞头文件”，该文件内 `#import` 的所有头文件都会被包含在模块中；`module * { export * }` 表示为 umbrella header 中的每个头文件自动创建子模块，并导出所有子模块的内容，使使用者可以直接访问 [11]。

**Q：如果想在 SPM 中引用一个本地 Framework 作为依赖，该怎么做？**
A：可以在 `Package.swift` 中使用 `.package(path: "path/to/local/package")` 并指定版本范围，然后在目标依赖中添加该包的产品名称 [7][9]。注意该本地包本身可以是一个 Swift Package 或通过 `.package(path:)` 引用的任何 Swift Package 目录。
