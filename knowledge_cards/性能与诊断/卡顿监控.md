# 卡顿监控

## 一句话总结
卡顿监控通过注册 RunLoop Observer 监听主线程状态，在子线程中定时检查主线程是否长时间停留在 `kCFRunLoopBeforeSources` 或 `kCFRunLoopAfterWaiting` 等状态，超过阈值则判定为卡顿并采集当前线程堆栈以定位耗时代码。[3][4][7]

## 核心原理

1. **RunLoop 状态序列**
   RunLoop 每次循环依次经历 `BeforeTimers → BeforeSources → 处理 Source0 → BeforeWaiting → 休眠 → AfterWaiting → 处理事件` 等状态。其中 **`BeforeSources`** 和 **`AfterWaiting`** 是执行用户代码的关键阶段，若主线程在这些状态上停留过久，说明正在执行耗时任务。[7][10]

2. **子线程 Watchdog 机制**
   开启一个独立子线程，通过信号量（`DispatchSemaphore`）等待主线程 RunLoop 状态变化的通知。若等待超时（如 100ms、2s 等阈值），同时主线程当前处于 `kCFRunLoopBeforeSources` 或 `kCFRunLoopAfterWaiting` 状态，则判定为卡顿，触发堆栈采集。[3][5][7]
   伪代码示意：[5]
   ```swift
   while true {
       let status = semaphore.wait(timeout: .now() + .milliseconds(500))
       if status == .timedOut {
           if mainThreadState == .beforeSources || mainThreadState == .afterWaiting {
               captureAllThreadBacktraces()
           }
       }
   }
   ```

3. **堆栈采集方法**
   向主线程发送 `SIGURG` 信号触发 `backtrace`，获取主线程当前真实堆栈。[7][10] 部分方案也直接使用 `thread_info` 等 Mach API 读取线程状态。[5]

4. **阈值与策略**
   - 微信 Matrix：主线程超时阈值 2 秒，子线程检查周期 1 秒；同时监控单核 CPU 占用 > 80% 也视为卡顿。[6]
   - 通用建议：阈值多为 100ms 或连续多次超时（如连续 5 次超时 50ms，或连续 3 次超时 80ms）以降低误报。[9][10]
   - 卡死升级（字节 Heimdallr）：阈值 T1（如 250ms）算卡顿抓栈，T2（如 8s）算卡死，上报所有线程堆栈。[5]

5. **双 Observer 方案解决 BeforeWaiting 盲区**
   简单方案（单个 Observer，order=0）存在监控盲区：`kCFRunLoopBeforeWaiting` 阶段中系统 Observer 会执行 UI 布局、绘制、手势回调等，其耗时无法被捕获。微信 Matrix 通过注册两个 Observer（order 分别为 `LONG_MIN` 和 `LONG_MAX`）包裹所有系统 Observer，从而完整覆盖该阶段。[4][10]

6. **扩展优化**
   - **退火采样**：卡顿持续时每隔 200ms 再抓一次栈，相同栈计数超过阈值才判定为“真实”卡顿点，避免掐在无关栈帧上。[5]
   - **后台过滤**：App 进入后台被 suspend 时主线程不运行，需排除此类误报。[5]
   - **死锁判定**：通过 `thread_info` 读取 `run_state`，若为 `TH_STATE_WAITING` 且栈顶包含 `__psynch_mutexwait` / `semaphore_wait_trap` / `dispatch_sync_wait`，则为死锁嫌疑；进一步读取锁的持有者 tid 构建等待图，判环即死锁。[5]
   - **Sentry App Hangs**：默认 2s 阈值，区分 **fully-blocking**（无响应）与 **non-fully-blocking**（延迟但恢复），后者以“non-fatal hang”上报。[12]

7. **其他卡顿检测手段对比**
   - CADisplayLink FPS 检测：只能提示掉帧，无法定位代码位置，主线程阻塞时自身也会延迟。[10]
   - 子线程 Ping 方案：通过 `DispatchQueue.main.async` 派发标志位任务，主线程若超时未响应则阻塞，实现简单但精度受限。[10]
   - MetricKit（iOS 13+）：系统级无额外开销，收集卡顿时间分布直方图，iOS 14+ 可获取卡顿堆栈（`MXCallStackTree`），但每日回调一次，非实时。[10]
   - Instruments 系统工具：Time Profiler、Core Animation、System Trace，仅开发阶段可用。[10]
   - Firebase Crashlytics 集成 MetricKit Hang （2024 下半年开始）。[12]

## 关键细节与易错点

1. **为什么不能只靠一个 Observer 回调？**
   单个 Observer（order=0）会在系统 Observer 之后、`BeforeWaiting` 之前被回调，而此时系统 Observer 执行的 UI 布局、绘制等耗时任务已结束，监控不到该阶段的卡顿。需注册 dual Observer 包裹系统 Observer 才能捕获。[1][4]

2. **堆栈采集的时机**
   卡顿时主线程可能处于阻塞状态，直接调用 `backtrace` 函数不一定能获取正确堆栈（因为主线程栈指针可能变化）。通过发送 `SIGURG` 信号强制信号处理函数在主线程上下文执行，从而获取实时堆栈。[7][10]

3. **子线程保活注意事项**
   - 必须向子线程 RunLoop 添加 Source（如 NSPort），否则 `CFRunLoopRunSpecific` 会因 `__CFRunLoopModeIsEmpty` 直接返回。[3][4]
   - 避免使用 `[NSRunLoop run]`（无法被 `CFRunLoopStop` 停止），推荐 `while + runMode:beforeDate:` 配合标志位控制退出。[3][4]

4. **阈值设定平衡**
   阈值过短（如 < 50ms）可能频繁误报（如图形渲染耗时），过长则卡顿已发生但未被捕捉。业界常见 100ms~2s。微信采用 2s 阈值检查周期 1s，侧重捕获严重卡顿。[6][9]

5. **后台状态过滤**
   若 App 被系统挂起，主线程 RunLoop 不再处理事件，其状态可能是 `BeforeWaiting`，此时检测会误报。需检查 App 是否在前台活跃。[5]

6. **卡死与卡顿的关系**
   卡死（ANR）是卡顿的极端情况：主线程长时间无响应（通常 > 5s 或 Watchdog 超时）。Watchdog 超时错误码 `0x8BADF00D` 常见于启动阶段 20s 未完成或主线程阻塞。[11] 可用双阈值（T1/T2）实现卡顿→卡死的升级上报。[5]

7. **死锁检测与卡顿检测的关系**
   卡顿检测发现主线程长时间在 `AfterWaiting` 等状态，可进一步通过 `thread_info` 分析线程运行状态（`TH_STATE_WAITING`）和栈顶函数判断死锁。死锁检测需要构建锁的等待/持有图。[5]

## 高频追问

### Q1: 如何区分卡顿和卡死？

- 卡顿：主线程在规定时间（如 250ms）内未完成 RunLoop 状态切换，但仍在执行任务。
- 卡死：主线程持续阻塞超过更长时间（如 8s）无响应，通常被系统 Watchdog 以 `0x8BADF00D` 杀死。[5][11]

实际方案常设双阈值：较短阈值（如 250ms）触发卡顿堆栈采集，较长阈值（如 8s）触发卡死堆栈上报所有线程。[5]

### Q2: 为什么简单 RunLoop Observer 方案不能监控 `kCFRunLoopBeforeWaiting` 阶段的卡顿？

简单方案（order=0）的 Observer 在所有系统 Observer 之后、进入休眠前被回调。而系统 Observer（order 介于 `LONG_MIN` 和 `LONG_MAX` 之间）在 `kCFRunLoopBeforeWaiting` 阶段实际执行了 UI 布局、绘制、手势回调等耗时操作，当这些操作卡顿时，已经过了简单 Observer 回调点，无法被检测到。通过注册 order 分别为 `LONG_MIN` 和 `LONG_MAX` 的两个 Observer，可以包裹住全部系统 Observer，监控到该阶段的消耗。[4][10]

### Q3: 如何采集主线程卡顿时的真实堆栈？

不能直接在主线程外调用 `backtrace`。业界方案是向主线程发送 `SIGURG` 信号，该信号会中断主线程当前执行流，触发信号处理函数（在非阻塞的信号上下文中）调用 `backtrace` 获取堆栈。使用 `SIGURG` 而非 `SIGSTOP` 是因为它不会被系统限制且不会导致进程暂停。[7][10]

### Q4: 卡顿监控中如何减少误报？

- **退火采样**：卡顿持续时每 200ms 再抓一次栈，相同栈计数累积超过阈值才确认卡顿点。[5]
- **后台过滤**：检查 App 是否在前台活跃（如 `UIApplicationState`），排除被 suspend 后主线程不跑的情况。[5]
- **CPU 阈值辅助**：仅当 CPU 占用高（如单核 > 80%）且状态停留才判定卡顿，避免因系统调度导致的短暂等待。[6]
- **连续超时策略**：如连续 3 次或 5 次超时才算真正卡顿。[9]

### Q5: RunLoop Observer 监控与 CADisplayLink FPS 方案有何区别？

- RunLoop Observer 直接在 RunLoop 状态变化点检测，能捕获主线程阻塞在哪一步，并采集堆栈定位代码。[7][10]
- CADisplayLink 只能通过回调是否按时触发判断是否掉帧，无法知道具体代码段，且主线程阻塞时自身回调也会被推迟。[10]
- 两者可互补：开发阶段用 FPS 快速感知卡顿，线上用 Observer 堆栈定位根因。

### Q6: MetricKit 能否替代 RunLoop Observer 线上监控？

MetricKit 由系统底层收集卡顿数据，零额外开销，能获取 `MXHangDiagnostic` 和堆栈（iOS 14+），但数据是**每日回调一次**，非实时。适合长期趋势监控和版本对比，不适合实时告警或复现排查。RunLoop Observer 方案可实时上传卡顿堆栈，便于快速响应。[10]

### Q7: 卡顿检测到的堆栈中哪些信号表明是死锁？

若主线程卡在 `AfterWaiting` 状态，堆栈中包含 `__psynch_mutexwait`、`semaphore_wait_trap`、`dispatch_sync_wait` 等函数，且通过 `thread_info` 读取线程运行状态为 `TH_STATE_WAITING`、CPU 占用为 0，则死锁嫌疑很大。进一步从锁结构体读取持有者 tid，若有环状依赖，可确认死锁。[5]

### Q8: 对于 `tableView:didSelectRowAtIndexPath:` 这类场景，简单方案为什么可能检测不到卡顿？

该回调属于 Source0 事件处理，发生在 `kCFRunLoopBeforeSources` → `AfterWaiting` 之间。但简单单 Observer 方案在 `BeforeSources` 之后、系统 Observer 之前注册，若系统 Observer 没有卡顿，而用户代码（如 `didSelectRow`）执行耗时，会停留在 `BeforeSources` 或 `AfterWaiting` 状态，理论上应能被检测到。实际失效可能来源于阈值设置不当、子线程与主线程状态同步延迟，或使用了仅监控 `kCFRunLoopEntry`/`kCFRunLoopExit` 的 Observer。正确做法是同时监控 `BeforeSources` 和 `AfterWaiting`，并确保子线程状态更新逻辑正确。[8][9] （注：材料未给出具体原因，这里仅泛述已知可能性）
