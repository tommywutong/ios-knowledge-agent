# 启动性能优化

## 一句话总结
iOS App 启动性能优化的核心目标是让用户在 400 毫秒内看到首帧且可交互，优化需分别处理 pre-main 阶段（dyld 链接、Runtime 初始化）和 main 后阶段（业务代码执行），并通过 Instruments 等工具量化各阶段耗时 [2][4][5][11]。

## 核心原理

- **启动阶段划分**：App 启动分为 pre-main 和 main 后两大阶段。pre-main 阶段由 dyld 完成动态库链接、Runtime 初始化（包括 `+load`、静态构造、`+initialize` 等），main 后阶段执行 `application(_:didFinishLaunchingWithOptions:)`、创建视图、加载内容直至生成首帧。 [1][4][8]
- **首帧时间目标**：Apple 2019 年 WWDC 提出的目标是 “rendering our first frame within 400 milliseconds”。其中系统侧初始化约占用 100 毫秒，留给开发者约 300 毫秒来创建视图、加载内容并生成首帧。首帧不必完全加载完成，允许放置异步加载占位符，但应用必须已可交互和响应。 [2]
- **测量方法**：
  - 使用 Xcode Instruments 的 **App Launch** 模板（整合 Time Profiler、Virtual Memory、System Trace）进行冷启动录制，可查看 pre-main 与 main 后各阶段耗时、函数调用序列。 [4][11][12]
  - 配合 `DYLD_PRINT_STATISTICS` 环境变量打印 dyld 统计信息，以及 `os_signpost` 对 **First Meaningful Paint**（首帧）打点，形成可复盘的量化指标。 [4][12]
  - 通过 Xcode Organizer 的 **Launch Time** 面板可查看 App 在用户设备上的平均 “time to first frame” 历史趋势（近 16 版本）。 [7]
- **优化方向**：
  - **Pre-main 阶段**：减少加载工作量，包括动态库数量裁剪（将不必要的动态库改为静态库或合并）、将 `+load` 方法迁移到 `+initialize` 或首帧后调用、利用二进制重排减少缺页中断。 [4][8]
  - **Main 后阶段**：分析 `application(_:didFinishLaunchingWithOptions:)` 热点，主线程避免执行大文件读取等高耗时操作；将非首帧必需的逻辑延后执行（如网络请求限制条数、延迟刷新操作）。 [4][10]

## 关键细节与易错点

- **400 毫秒不是 pre-main 的预算**：常见误解是把 400 毫秒当作 pre-main 阶段的预算，实际上 2016 年与 2019 年两版 WWDC 均指从用户点击图标到首帧渲染的全部时间。2016 年 session 406 明确说明该时间包含 `UIApplicationMain` + nib 加载 + App Delegate 回调；2019 年 session 423 则说明系统先占用约 100 毫秒，留给开发者约 300 毫秒。Apple 现行文档中已不再明确给出 400 毫秒数值。 [2][5]
- **冷启动、热启动与恢复（resume）不能混淆**：测量时应确保是冷启动（app 未被系统保留在内存中），通常通过重启设备或使用 Instruments 冷启动录制来保证。热启动或恢复不是真的启动，其耗时不能与启动优化目标混为一谈。 [2][3]
- **测量使用 Release 配置**：使用 App Launch 模板时应使用 Release Scheme，以便获得真实性能数据；当深入分析具体方法调用栈时，才切换到 Debug Scheme 以获取符号化信息。 [10]
- **首帧可含占位符**：首帧不必是最终渲染完成的状态，但必须让用户能交互。例如地图 App 可能先显示部分瓦片，用户仍可执行搜索。 [2]
- **动态库链接影响启动速度**：将部分代码从静态库改为动态库虽可减少二进制体积，但 pre-main 阶段 dyld 需要链接这些动态库，会延长启动时间。评估时需要权衡体积优化与启动性能。 [1]
- **性能调试建议测渲染时间而非 FPS**：帧渲染时间线性反映性能变化，FPS 是倒数，在光照变化等场景下可能产生测量偏差。此建议虽非启动优化专用，但适用于首帧渲染阶段的调优。 [6]

## 高频追问

**Q1：如何区分 pre-main 和 main 后的启动时间？**
使用 Instruments App Launch 模板可直观看到 **Pre-main** 和 **Post-main** 的时间分割线。也可通过环境变量 `DYLD_PRINT_STATISTICS` 获取 dyld 阶段耗时。Xcode Organizer 的 Launch Time 面板同样以 pre-main 和 main 后分类展示。 [4][11][12]

**Q2：为什么减少动态库对启动有帮助？**
Pre-main 阶段 dyld 需要将 App 依赖的所有动态库链接到目标进程，动态库越多，链接时间越长。将不必要的动态库合并或转为静态库可直接减少 dyld 的工作量。 [1][4][8]

**Q3：`+load` 和 `+initialize` 哪个对启动影响更大？**
`+load` 是在 pre-main 阶段 Runtime 初始化期间加载所有类时同步调用的，会直接延长 pre-main 时间；`+initialize` 是惰性调用（首次发送消息时），不会阻塞 pre-main。因此优化策略是将 `+load` 中的逻辑迁移到 `+initialize` 或更晚时机执行。 [4][8]

**Q4：如何处理首帧必须展示的数据加载瓶颈？**
核心原则是只加载首帧渲染必需的数据，对非首帧必需的逻辑进行延迟（defer）。具体做法包括：限制网络请求的条数、减少 Core Data 批量加载的实体数、将部分刷新方法移到首帧渲染完成后执行。同时用 Instruments 识别最耗方法并针对性优化。 [4][10]

**Q5：400 毫秒是不是 Apple 给 pre-main 的硬性指标？**
不是。400 毫秒是冷启动从用户点击图标到首帧渲染的总时间目标（2016 年 session 406），2019 年 session 423 明确说系统自己先占约 100 毫秒，留给开发者约 300 毫秒。现行 Apple 文档中不再出现这个数值，但业界仍将其作为参考基准。 [2][5]

**Q6：如何验证启动优化效果？**
使用 Instruments App Launch 模板录制冷启动，对比优化前后的 pre-main 和 main 后耗时；配合 `os_signpost` 对 First Meaningful Paint 打点，在 Xcode Organizer Launch Time 面板观察用户设备上的平均首帧用时趋势。注意始终使用 Release 配置录制。 [4][12][7]
