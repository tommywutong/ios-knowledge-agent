# 同步异步与队列

## 一句话总结

同步（`dispatch_sync`）阻塞当前线程直到任务完成，尽量复用调用线程；异步（`dispatch_async`）立即返回，由系统在合适线程上调度执行。队列类型（串行/并发/主队列）决定任务的执行顺序和并发能力，`dispatch_barrier` 在自定义并发队列上提供写独占屏障。

## 核心原理

### 1. 同步与异步的本质

- `dispatch_sync` 提交 block 到队列并等待其执行完毕才返回。作为性能优化，只要可能就在**当前线程**上执行该 block，但提交给主队列的 block 始终在主线程执行 [10]。同步不开新线程，任务在执行 `sync` 的线程上串行执行 [6]。
- `dispatch_async` 提交 block 后立即返回，不阻塞调用线程。由系统从线程池中分配线程执行，线程可能变化 [5][12]。

### 2. 队列类型

- **串行队列**（Serial Queue）：任务按 FIFO 一个接一个执行，同一时间只有一个任务。`dispatch_queue_create("label", DISPATCH_QUEUE_SERIAL)` [9]。
- **并发队列**（Concurrent Queue）：任务可并发执行，系统根据 CPU 核心数等因素控制线程数量，开发者无法直接控制 [9]。`dispatch_queue_create("label", DISPATCH_QUEUE_CONCURRENT)` [9]。
- **主队列**（Main Queue）：特殊的串行队列，任务在主线程上执行，用于 UI 更新 [9]。
- **全局并发队列**（Global Queue）：系统提供的并发队列，全局共享，通过 Quality of Service（QoS）指定优先级：`QOS_CLASS_USER_INTERACTIVE` > `QOS_CLASS_USER_INITIATED` > `QOS_CLASS_DEFAULT` > `QOS_CLASS_UTILITY` > `QOS_CLASS_BACKGROUND` [9]。

### 3. 队列与线程的关系

- 队列不是线程，同一队列的不同任务可能落在不同线程上（`async` 时），而 `sync` 任务通常复用在调用线程上 [5]。
- 示例：对一个串行队列连续 10 次 `async`，落到了 9 条不同线程；而 10 次 `sync` 全部落在调用线程（主线程）[5]。
- 不同队列也可以共用同一线程 [5]。
- 因此线程局部存储（TLS）在 GCD 任务中不可靠；`[NSThread currentThread]` 的属性可能随块不同而变化；可重入锁在 `dispatch_async` 的不同 block 之间无意义 [5]。
- 并发队列上，当线程阻塞时，GCD 会创建更多线程来消耗剩余任务，可能导致大量线程产生，引起上下文切换开销 [12]。

### 4. Dispatch Barrier（栅栏）

- `dispatch_barrier_async` 和 `dispatch_barrier_sync` 用于自定义并发队列的写操作，确保 barrier 任务执行时队列中无其他任务，且 barrier 任务执行完毕后才恢复并发执行 [1][2]。
- 在串行队列中无需使用 barrier，因为串行本身一次只执行一个任务 [1]。
- 在全局并发队列中使用 barrier 无效，效果等价于普通的 `dispatch_async` / `dispatch_sync` [1][8]。
- 典型用法：读写锁封装——读操作使用 `dispatch_sync`，写操作使用 `dispatch_barrier_async`，允许多个读同时进行，写时独占 [2]。

### 5. Dispatch Group

- `dispatch_group_notify` 在 group 中所有关联任务完成后，将 block 提交到指定队列 [7]。
- 可通过 `dispatch_group_async` 或手动调用 `dispatch_group_enter`/`dispatch_group_leave` 管理任务组 [7]。
- 适用队列：自定义串行队列、主队列（注意 `dispatch_group_wait` 在主线程应谨慎使用）、并发队列 [7]。

### 6. NSOperationQueue 与 GCD

- NSOperationQueue 底层使用 `libdispatch`（GCD）框架来启动操作的执行，其操作总是在单独线程上执行，无论操作是同步还是异步 [11]。

## 关键细节与易错点

### 1. 不同组合的行为

| 组合 | 串行队列 | 并发队列 | 主队列 |
|------|----------|----------|--------|
| sync (同步) | 不开新线程，串行执行 | 不开新线程，串行执行（在调用线程） | 在主线程调用会死锁；在子线程调用则不会死锁，任务在主线程执行 |
| async (异步) | 开1条新线程，串行执行 | 开多条新线程，并发执行 | 不开新线程，串行执行（在主线程） |

[6]

### 2. 死锁条件

- **串行队列内 `dispatch_sync` 到同一串行队列**：必然死锁。任务 A 在队列中等待完成，内部又同步提交任务 B 到同一队列，B 必须等 A 完成，形成循环等待 [3][10]。
- **主队列 + sync 在主线程调用**：死锁。因为主队列也是串行队列，主线程正在执行调用 `dispatch_sync` 的代码（即当前任务），`sync` 提交的任务需要等当前任务完成，但当前任务在等待 sync 返回 [3][6]。
- **并发队列内 `dispatch_sync` 到同一并发队列**：安全，不会死锁。因为 `sync` 不要求队列独占所有权，直接在调用线程上执行 [4]。
- **并发队列内 `dispatch_barrier_sync` 到同一并发队列**：死锁。barrier 要求队列上没有别的任务在跑，而调用它的 block 本身就在跑，条件永远无法满足，libdispatch 不自检此情况，线程真挂起 [4]。
- **不同串行队列间 `dispatch_sync`**：只要目标队列不是当前队列，不会死锁 [3]。

### 3. barrier 在全局队列中无效

在全局并发队列（`dispatch_get_global_queue`）中使用 `dispatch_barrier_async` 或 `dispatch_barrier_sync` 不会起到屏障作用，效果等同于 `dispatch_async` / `dispatch_sync` [1][8]。

### 4. 性能优化与线程复用

`dispatch_sync` 会在当前线程执行 block 作为性能优化，但提交到主队列的 block 总是运行在主线程 [10]。因此说法“并发队列同步执行只会在主线程执行”不准确，实际是在调用线程（可能是任意线程）[10]。

### 5. barrier block 的执行时机

`dispatch_barrier_async` 提交的 barrier block 会等待所有先于它提交的任务（包括在它之后提交但先于它开始执行的任务？）完成，然后开始执行，执行期间队列不处理其他任务，完成后恢复并发 [1][2][8]。

## 高频追问

**Q1: 为什么在串行队列中调用 `dispatch_sync` 向同一个串行队列提交任务会死锁？**

A: 因为串行队列一次只执行一个任务。当前正在执行的任务（假设为 B）调用了 `dispatch_sync`，向同一个队列提交另一个任务 C。C 必须等待 B 完成才能开始执行，但 B 的完成又依赖于 C 的完成（因为 `dispatch_sync` 会阻塞直到 C 执行完毕），形成循环等待 [3]。[材料补充：如果在主线程调用主队列的同步任务同样会导致死锁][3]。

**Q2: 并发队列中 `dispatch_sync` 到自身为什么不会死锁，而 `dispatch_barrier_sync` 会？**

A: `dispatch_sync` 到并发队列时，不需要队列给予独占所有权，可以直接在调用线程上执行该 block，因此不会等待队列空闲 [4]。而 `dispatch_barrier_sync` 要求队列上没有其他任务正在执行，且 barrier 任务需要独占执行权。调用者所在的 block 本身就是当前队列上的一个任务，导致条件永远无法满足，从而挂起 [4]。libdispatch 的自检覆盖串行队列的所有权环，但不覆盖 barrier 的这种自等 [4]。

**Q3: 使用 `dispatch_barrier_async` 时，在全局并发队列中能起到独占写的作用吗？**

A: 不能。`dispatch_barrier_async` 只在自己创建的自定义并发队列上起到屏障作用，在全局并发队列和串行队列上效果与 `dispatch_sync` / `dispatch_async` 一样 [1][8]。因为系统也在使用全局队列，barrier 会堵塞其他任务执行 [1]。

**Q4: 同步执行一定在主线程吗？**

A: 不准确。`dispatch_sync` 的 block 默认在调用线程上执行（作为性能优化），但有一个例外：提交到主队列的 block 总是在主线程执行 [10]。因此并发队列同步执行可能在任意线程（调用线程），不一定是主线程。[材料说明：“并发队列 + sync”不开新线程，串行执行，任务在当前线程执行][6]。

**Q5: 异步任务会在新线程执行吗？串行队列异步会开辟几条线程？**

A: 异步任务不一定在新线程，但通常由系统分配线程，可能复用已有线程 [5]。串行队列异步只会开启一条新线程（因为同一时间只执行一个任务），任务按序在该线程上执行 [6]。并发队列异步会开启多条线程并发执行，具体数量由 GCD 根据系统资源决定 [6][9]。

**Q6: `dispatch_group_notify` 什么时候触发？**

A: 当 group 中所有关联的任务（通过 `dispatch_group_async` 或手动 `enter`/`leave` 管理的任务）都执行完毕后，`dispatch_group_notify` 会立即将 block 提交到指定队列 [7]。如果 group 没有关联任何任务，则立即提交 [7]。

**Q7: NSOperationQueue 与 GCD 的关系如何？**

A: 官方文档指出，操作队列（OperationQueue）使用 `Dispatch` 框架（即 libdispatch）来启动其操作的执行，且队列总是在单独线程上调用操作，无论操作是同步还是异步 [11]。这属于公开的实现细节。

**Q8: 在 reader block 中调用了 writer 方法（内部使用 barrier），可能有什么风险？**

A: 如果 writer 方法使用 `dispatch_barrier_sync` 提交到同一个并发队列，会导致死锁。因为 reader block 本身是并发队列上的一个任务，而 `dispatch_barrier_sync` 要求队列上没有其他任务运行，导致条件无法满足 [4]。这是写读写锁封装时容易踩的坑。

**Q9: 线程局部存储（TLS）在 GCD 任务中可靠吗？**

A: 不可靠。同一个队列的不同 `async` 任务可能落在不同线程上 [5]；即使 `sync` 落在调用线程，也不能保证所有任务在同一线程。因此 `[NSThread currentThread]` 的属性、`threadDictionary` 等在不同 block 间可能无法共享 [5]。可重入锁在 `dispatch_async` 的不同 block 之间也没有意义 [5]。
