# 后台网络传输

## 一句话总结

后台 URLSession（background URLSession）让下载和上传任务在 app 被系统挂起或终止后仍继续运行，并自动支持断点续传（resumable transfers）和联网等待，适合大文件或长时间的网络传输。 [1][11]

## 核心原理

1. **后台 Session 的创建**
   使用 `URLSessionConfiguration.background(withIdentifier:)` 创建后台配置，然后通过该配置创建 `URLSession` 实例。系统会将此 identifier 与后台守护进程关联，以便在 app 进程外部继续执行任务。 [3][11][12]

2. **任务类型支持**
   - 后台 session **支持** `URLSessionDownloadTask` 和 `URLSessionUploadTask`。
   - 后台 session **不支持** `URLSessionDataTask`。 [8]

3. **断点续传机制**
   - 如果服务器支持（通过响应头 `Accept-Ranges: bytes` 和 `ETag` 标识资源），系统会自动处理下载和上传任务的断点续传。 [1][2]
   - 任务中断后，系统会以递增的时间间隔尝试恢复；若无法恢复则从头重试。 [1]
   - 开发者也可以手动调用 `downloadTask(withResumeData:)` 传入之前保存的 resumeData 来恢复下载。 [4][9]

4. **生命周期与进程管理**
   后台任务由系统调度，在独立于 app 的进程中执行。即使 app 被挂起、崩溃或被系统杀死，网络传输仍会继续。当任务完成时，系统会通过 `application:handleEventsForBackgroundURLSession:completionHandler:` 唤起 app（iOS）。 [1][10][11]

5. **网络可用性等待**
   设置 `waitsForConnectivity = true` 后，当设备没有网络连接时，任务会等待，直到设备重新联网再被调度。 [1][3]

## 关键细节与易错点

- **后台 Session 的配置选项**
  - `isDiscretionary`：允许系统选择最佳时机（如仅在 Wi-Fi、充电时）执行任务。
  - `sessionSendsLaunchEvents`：控制任务完成时是否唤起 app。
  - `waitsForConnectivity`：等待网络而不是立即失败。
  - `allowsCellularAccess`：限制是否使用蜂窝网络。 [3]

  **注意**：这些选项仅在后台 session 中生效，且应谨慎使用以避免资源浪费或用户意外请求。

- **委托方法接收进度**
  要获取下载进度（如已写入字节数、预期总字节数），必须实现 `URLSessionDownloadDelegate` 和 `URLSessionTaskDelegate` 协议。 [6]
  恢复下载时会调用 `urlSession(_:downloadTask:didResumeAtOffset:expectedTotalBytes:)`，参数 `fileOffset` 表示已下载数据大小，若服务器禁止恢复则为 0。 [4]

- **资源超时控制**
  通过 `timeoutIntervalForResource` 可设置整个传输允许的最大时间（例如用于内容有限时效或 Wi-Fi 带宽不足的场景）。 [7]

- **App Extension 中使用**
  App Extension 可以创建后台 session 发起上传/下载任务，即使扩展终止，任务仍会继续；任务完成时系统会唤起宿主 app。 [10]

- **Swift Concurrency 集成**
  在 SwiftUI 的 background task 中，可以利用 `withTaskCancellationHandler` 将即将被取消的即时网络请求提升为后台下载任务，系统会自动去重同一 URLSession 内的请求。 [5]

## 高频追问

**Q1：后台 session 是否支持 data task？**
不支持。后台 session 仅支持 download task 和 upload task。 [8]

**Q2：断点续传需要服务器满足什么条件？**
服务器需要在响应头中包含 `Accept-Ranges: bytes` 并返回 `ETag` 以唯一标识资源。若资源内容变化，ETag 也会变，导致无法恢复。 [2]

**Q3：系统在什么情况下会重新尝试被中断的任务？**
系统会以递增的时间间隔尝试恢复；如果无法恢复（例如服务器不支持断点），则从头开始重试。 [1]
如果设备离线，任务会一直等待直到网络可用（需设置 `waitsForConnectivity`）。 [1]

**Q4：后台任务完成后如何通知 app？**
在 iOS 中，系统会调用 `UIApplicationDelegate` 的 `application:handleEventsForBackgroundURLSession:completionHandler:` 方法。如果你使用 SwiftUI，可以通过 `.backgroundTask(.urlSession(withIdentifier: "..."))` 修饰符处理。 [10][5]

**Q5：后台上传任务是否也能自动断点续传？**
是的，只要服务器支持，后台 session 会自动处理上传任务的断点续传，与下载类似。 [1]

**Q6：手动恢复下载时传入的 resumeData 从何而来？**
在下载任务被取消或失败时，可以从 `URLSessionDownloadTask` 的 `error` 对象的 `userInfo` 中提取 `NSURLSessionDownloadTaskResumeData` 键对应的 data。 [4]（材料中未直接说明 error 来源，但提到了保存 resumeData 的做法。）

**Q7：Background session 和 default session 有什么区别？**
- Default session 运行在 app 进程内，app 被挂起时任务停止。
- Background session 运行在独立进程，app 被系统挂起、崩溃或杀死后任务继续执行。 [11][12]
- Background session 支持自动重试和断点续传，而 default session 需要开发者手动处理。 [1]

**Q8：使用 background session 时是否需要担心电量消耗？**
系统会综合考虑电量、网络状况等因素来调度后台任务（如 `isDiscretionary` 选项），尽量高效利用系统资源。 [1][3] 但材料未提供具体功耗优化细节。
