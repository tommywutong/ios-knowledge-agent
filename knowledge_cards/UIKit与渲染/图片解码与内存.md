# 图片解码与内存

## 一句话总结

图片加载到内存后以未压缩的像素数据（bitmap）存放，尺寸越大占用内存越高；通过下采样（downsampling）在解码阶段直接输出小尺寸图片，可降低内存占用数倍以上，推荐使用 UIKit（`UIGraphicsImageRenderer`）、Core Graphics 或 Image I/O 实现，避免使用 Core Image 进行缩放。[1][2][3][4][7]

## 核心原理

- **内存占用来源**：图片文件（PNG/JPEG）被解码后，像素数据以未压缩形式（通常为 RGBA8，每像素 4 字节）存储在内存中。例如一张 512×512 的图片占用 512×512×4 ≈ 1 MB [4]。更极端的例子中，未下采样时一张大图占用 220.2 MB，下采样后仅 23.7 MB [2]。
- **下采样（downsampling）**：指将原图按目标显示尺寸缩小后再解码，避免将全尺寸像素数据加载到内存。实现方式包括：
  - 使用 `CGImageSource` 的 `kCGImageSourceThumbnailMaxPixelSize` 选项，在解码阶段直接生成缩略图，内存峰值只与目标尺寸相关，不会完整解码原图 [7]。
  - 使用 `UIGraphicsImageRenderer` 绘制到目标尺寸的上下文，通过 `makeImage()` 得到小尺寸 `CGImage` [1][3][11]。
  - 使用 Core Graphics 的 `CGContext` 绘制并触发解码 [12]。
- **推荐方案**：
  - iOS 平台推荐使用 `UIGraphicsImageRenderer`，与 Core Graphics、Image I/O 性能相近 [1][3]。
  - 如果已在工程中使用 `vImage` 可以继续使用，否则额外引入的工作量可能大于收益 [1][3]。
  - **不建议使用 Core Image 进行下采样**，Apple 官方 Performance Best Practices 指出应使用 Core Graphics 或 Image I/O 函数裁剪、下采样，而非 Core Image [1][3]。
- **强制解码（force decode）**：将图片绘制到位图上下文（`CGContext`）中，强制触发完整的像素解码过程，生成已解码的 `CGImage`，这样在 UI 线程显示时不再需要额外解码，常用于异步图片加载优化 [12]。

## 关键细节与易错点

1. **下采样尺寸计算**：`UIGraphicsImageRenderer` 接收的是 point 大小（逻辑点），需乘以 `UIScreen.main.scale` 得到 pixel 大小；而 `CGImageSource` 的 `maxPixelSize` 直接使用 pixel 值 [6]。
2. **`DownsamplingImageProcessor` vs `ResizingImageProcessor`**（以 Kingfisher 为例）：
   - `ResizingImageProcessor`：先将原图完整解码到内存（如 4000×3000 约 48 MB），再进行缩放。
   - `DownsamplingImageProcessor`：使用 `CGImageSource` 的缩略图选项，解码阶段直接输出目标尺寸，内存峰值小得多，优先用于列表场景 [7]。
3. **可拉伸图片（resizable image）可降低 GPU 内存**：使用 `UIImage resizableImageWithCapInsets:resizingMode:` 或 CALayer 的 `contentsCenter` 属性，用很小的源图渲染大尺寸 UI 元素，减少像素数据量和解码工作量 [10]。
4. **访问图片属性避免加载全图**：直接使用 `UIImage imageWithContentsOfFile:` 会完整加载图片到内存。应使用 `CGImageSource` 的 API 读取元数据（如尺寸、方向）而不解码像素数据 [4]。
5. **Core Image 下采样质量可控制**：通过 `CIContextOption` 的 `highQualityDownsample` 属性（默认 true）控制是否启用高质量下采样算法 [9]。但整体上 Core Image 不如其他方案高效 [1][3]。
6. **Photo Extension 内存限制**：处理图片时内存压力大，应使用系统提供的显示大小图片、限制 Core Graphics 上下文数量、优先使用 GPU（Core Image 或 GPUImage）串联滤镜以减少中间缓冲 [5]。

## 高频追问

**Q1: 如何降低 UIImage 加载时的内存峰值？**
A: 采用下采样，避免完整解码原图。推荐方案：使用 `CGImageSource` 的 `kCGImageSourceThumbnailMaxPixelSize`（Image I/O 方式）或 `UIGraphicsImageRenderer` 绘制到目标尺寸。下采样后内存占用可降低一个数量级（如 220.2 MB → 23.7 MB）[2][7]。

**Q2: 下采样和强制解码有什么区别？**
A: 下采样指在解码阶段就缩小输出尺寸，内存峰值只和目标尺寸相关；强制解码是指将图片绘制到位图上下文，触发一次完整的像素解码（不改变尺寸），目的是提前完成解码工作以避免在主线程解码造成卡顿 [7][12]。

**Q3: 为什么推荐用 `UIGraphicsImageRenderer` 而不是 Core Image 做缩放？**
A: 根据 Apple 官方文档和性能测试，Core Image 在缩放操作上性能不如 UIGraphicsImageRenderer、Core Graphics 和 Image I/O [1][3]。除非项目已在使用 vImage，否则无需引入更低层的 Accelerate API [1][3]。

**Q4: 如何获取图片尺寸而不加载完整图片？**
A: 使用 `CGImageSource` 通过文件 URL 或 data 创建，调用 `CGImageSourceCopyPropertiesAtIndex` 读取像素宽度/高度等属性，此时不会解码像素数据 [4]。

**Q5: 在 iOS 扩展（Photo Extension）中处理大图如何优化内存？**
A: 在交互编辑阶段使用系统提供的显示尺寸图片而非原图；限制 Core Graphics 上下文数量并复用；使用 Core Image 或 GPUImage 在 GPU 上串联滤镜减少中间缓冲 [5]。

**Q6: 什么是可拉伸图片？为什么能优化内存？**
A: 可拉伸图片通过设定 cap insets 或 contentsCenter，让系统只对源图的一小部分进行拉伸来填充目标区域，从而只需要解码很小的图片，减少像素上传到 GPU 的内存和带宽消耗 [10]。

**Q7: 强制解码后内存是否释放？**
A: 强制解码会生成新的已解码 `CGImage`，原 `UIImage` 的 `cgImage` 如果不再持有，可能被释放。但本质上解码后的像素数据仍占用内存，只是提前完成了解码工作。需要主动管理引用以避免内存泄漏 [12]（注：材料未详细讨论释放时机，此点部分基于通用知识，本卡片不做扩展）。
