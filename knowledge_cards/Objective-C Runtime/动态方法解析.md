# 动态方法解析

## 一句话总结
当消息发送在继承链上找不到 IMP 时，运行时在进入完整转发前，会调用 `resolveInstanceMethod:` / `resolveClassMethod:` 给类一次动态添加方法实现的机会。[2][4][11][12]

## 核心原理
1. **调用时机**：在慢速查找（`lookUpImpOrForward`）中，遍历完所有继承链仍未找到 IMP，且 `resolver` 标志位为 true（首次），则触发动态方法解析。[11][12]
2. **解析实例方法**：调用 `_class_resolveInstanceMethod`，最终向类发送 `+resolveInstanceMethod:` 消息。[1]
3. **解析类方法**：先调用 `_class_resolveClassMethod` 发送 `+resolveClassMethod:`，若未解析成功，再尝试 `+resolveInstanceMethod:`（因为元类也是类，类方法相当于元类的实例方法）。[1][8]
4. **手工发送消息**：运行时源码无法直接写 Objective‑C 语法，解析方法通过 `objc_msgSend` 手工发送。[5]
5. **不依赖返回值**：运行时在调用 resolver 后，不会根据返回值决定是否继续，而是通过 `lookUpImpOrNilTryCache` 重查方法表确认是否真的添加了 IMP。[3][5][8]
6. **入缓存**：解析成功添加的 IMP 会在后续 retry 中被缓存在类的 cache 中，下次直接走快速路径。[11][12]
7. **只执行一次**：通过 `triedResolver` 标志保证只解析一次，防止递归。[11][12]
8. **与消息转发关系**：动态解析是第一阶段，若失败则进入完整的消息转发流程（`forwardingTargetForSelector:` 等）。[7][2]

## 关键细节与易错点
- **解析类方法时的接收者**：`[Foo resolveClassMethod:]` 中 `self` 是 Foo 类本身，而不是元类；但动态添加方法时，需要向元类（`object_getClass(self)`）添加。[6][8]
- **类方法解析的二次尝试**：如果 `resolveClassMethod:` 返回 YES 但未添加方法，或未实现，运行时还会尝试 `resolveInstanceMethod:`（在元类上调用），因为元类的实例方法就是该类的方法。[1][8]
- **`respondsToSelector:` 会触发动态解析**：它带 `LOOKUP_RESOLVER` 标志，查不到时会尝试解析。[9] 如果 delegate 类实现了 `+resolveInstanceMethod:`，每次 `respondsToSelector:` 未命中都会调用一次 resolver，可能影响高频路径性能。[9]
- **`@dynamic` 与 CoreData 典型用法**：声明 `@dynamic` 告知编译器不生成存取器；运行时通过父类（如 `NSManagedObject`）重写 `resolveInstanceMethod:` 动态添加 getter/setter。[10]
- **方法类型编码必须正确**：`class_addMethod` 需要提供正确的 type encoding，否则可能引起 crash。[3][7]
- **解析在转发之前**：如果返回 NO 或未添加方法，则进入转发流程。[7]

## 高频追问
**“动态解析和消息转发有什么区别？”**
动态解析是第一层机会，让类在运行时添加实现；如果失败，则进入完整的消息转发机制（快速转发、常规转发），后者可以转发到其他对象。[7][2]

**“`resolveInstanceMethod` 返回 YES 和返回 NO 有什么区别？”**
从源码看，返回 YES 或 NO 不影响结果；运行时通过重查 IMP 是否存在来判断是否成功。[3][5] 但惯例上返回 YES 表示已添加，返回 NO 表示无法处理，由上层决定。

**“类方法动态解析为什么要调用两次 resolve 方法？”**
第一次调用 `resolveClassMethod:` 针对类方法；如果失败，再调用 `resolveInstanceMethod:` 是因为元类也模拟实例方法解析，便于兼容两种写法。[1][8]

**“如果我在 `resolveInstanceMethod:` 里再次调用同一个方法会死循环吗？”**
不会，因为 `triedResolver` 标记阻止再次解析，会直接进入转发或返回 forward IMP。[11][12]

**“动态解析能在分类中重写 `resolveInstanceMethod:` 吗？”**
可以，分类中重写会覆盖主类的实现（因为 method resolution 是通过消息发送调用的，遵循分类重写规则）。本卡片材料未直接讨论分类覆盖，但材料 [9] 说明任何实现了 `+resolveInstanceMethod:` 的类都会在未命中时被调用，分类重写行为同常规方法覆盖。

**“为什么说动态解析比转发效率高？”**
解析成功后 IMP 会被缓存，后续直接使用快速路径；而转发每次都要走完整转发流程。[3]

**“`respondsToSelector:` 触发动态解析会有什么后果？”**
如果父类或本类实现了 `resolveInstanceMethod:`，那么每次 `respondsToSelector:` 未命中时都会调用一次 resolver，可能导致性能问题，尤其在高频路径（如 delegate 回调）上。[9]

**“`@dynamic` 和 `@synthesize` 的区别？”**
`@synthesize` 让编译器自动生成 getter/setter；`@dynamic` 告诉编译器不生成，由开发者通过动态方法解析或运行时提供实现。[10]
