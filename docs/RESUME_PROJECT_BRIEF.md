# 简历项目简报：iOS 知识库与引用式问答系统

最后核对：2026-09-10。本页只使用已提交代码、实际命令输出和已保存的生产验证记录；未发布补丁及人工复核项明确标注。

## 可直接使用的项目表述

构建个人 iOS 知识库与引用式问答系统：将笔记、Apple 公开资料和固定版本源码索引为可回溯的证据，在 Cloudflare Pages 上实现混合检索、重排、邻块扩展与段落级引用校验；无可靠证据时返回 `no_evidence`，避免模型用常识伪造来源。

- 设计 Retrieval v2：并行融合 Vectorize 语义召回和两座 D1 FTS 召回，采用 RRF 去重、reranker 和邻块扩展；回答以实际文件与行号引用为交付约束。
- 建立版本化源码证据边界：区分 Apple `objc4-951.7`、`CF-1153.18-apple`、Apple libdispatch、Swift 开源实现与 GNUstep 参照实现，避免将参照实现误表述为 Apple 私有行为。
- 实现生产评测器和发布门禁：评测报告不保存模型正文，支持无网络重算模式准确率、no-evidence 分类指标、引用覆盖率、锚点覆盖率和失败归因；门禁阻断锚点失效、追问夹具缺失、人工复核项和线上失败。
- 设计安全与可观测性：模型空流重试、NDJSON 流状态、额度退款、引用格式校验、个人资料最小暴露和指标正文脱敏。

## 面试追问

**为什么同时使用向量检索和 FTS？**

向量召回负责中英文语义表达，FTS 负责 `objc_msgSend`、`CFRunLoopRunSpecific` 这类精确符号。RRF 只融合排名，避免不同召回通道的原始分数不可比；之后再用 reranker 处理语义相关性。

**为什么要做邻块扩展？**

chunk 的命中片段可能缺少前置条件或结论。以 `file_key + chunk_ordinal` 获取相邻块，可补上下文，同时避免扫描整张 FTS 表。引用仍回到原始片段及行号。

**no_evidence 为什么是产品能力而不是失败？**

在受限知识库里，无法证明的问题若改走通用模型会破坏“可引用”的承诺。把缺证据建模为 `422 no_evidence`，同时退款且不调用生成模型，让资料缺口、召回问题和路由错误可独立诊断。

**如何评测而不泄露个人资料或模型内容？**

评测器只保存状态、模式、引用编号、公开化来源路径、行号和长度；不保存问题正文、答案正文、令牌或 Cookie。离线汇总直接读取这些脱敏字段，因此指标可复算。

**为什么源码要区分 Apple、Swift 和 GNUstep？**

它们的证据地位不同。Apple 公开源码能证明对应 drop 的实现；Swift 开源实现是跨平台参考；GNUstep 仅是非 Apple 的参照。分型可防止把合理推测包装为 Apple 行为事实。

## 当前限制

- 隔离网站副本中的 `3dd5617` 修复了 WidgetKit 流终结和 Kotlin/GCD 双侧证据要求，但只做了本地验证，尚未发布生产。
- 当前 P0 门禁仍保留 10 个人工复核项；评测集不能因“门禁变绿”而删去人工审查。
- 本地分层源码库尚未按稳定 ID 流程重新发布到 Vectorize/D1，不能宣称生产已使用 `objc4-951.7` 等新增来源。
- 已有指标衡量路由、引用和契约符合度，不涵盖人工事实正确性、答案完整性、延迟分位数或真实用户满意度；这些需要后续人工标注和生产观测。
